## 1. Project Description

### 1.1 What Is HomeCare Pro?

HomeCare Pro is a **HIPAA-compliant home care management platform** built to manage all aspects of a home-healthcare agency's operations: client management, staff scheduling, care plan creation, visit documentation, clinical charting (vitals, progress notes, medications), billing & invoicing, payroll & timesheets, insurance claims, reports & compliance dashboards, and role-based administrative settings.

It is a production-deployed **multi-tenant SaaS application** where each tenant is an `Organization` with one or more `Branch` locations.

### 1.4 Multi-Tenant Data Model

Every data-bearing entity is scoped to an `organizationId`. Key tenancy chain:

```
Organization (root tenant)
 └── Branch (regional office)
      └── User (login identity, RBAC role)
           ├── Staff (1:1, employee profile with payType, skills, certifications, availability)
           └── Client (1:1 optional, patient profile with medical info, medications, documents)
```

### 1.5 RBAC Role Hierarchy

Roles are hierarchical: `SUPER_ADMIN (6) > ADMIN (5) > MANAGER (4) > SUPERVISOR (3) > STAFF (2) > CLIENT (1)`.

The `hasRoleAccess()` utility (in `src/lib/utils.js`) checks whether a user's numeric level ≥ any of the required roles. Some API routes enforce specific role checks (e.g. billing requires ADMIN/MANAGER/SUPERVISOR), while others only check session existence.

## 4. Review Categories

Each review category below is specifically tailored to the patterns, architecture, and domain of the homecare-pro codebase. Codex must evaluate every file against all applicable categories.

---

### Category 1: Authentication & Authorization

**What to audit:**
- Session validation consistency across all API routes (some use `session?.user`, others check differently)
- RBAC enforcement — does every route that needs it call `hasRoleAccess()` with the correct roles?
- JWT token contents — are sensitive fields (like `organizationId`) always propagated?
- `organizationId` scoping — is every Prisma query filtered by `session.user.organizationId` to prevent cross-tenant data leakage?
- Auth callback security — does `authorize()` handle edge cases (disabled users, missing passwords)?
- Session duration — is the 8-hour HIPAA session limit correctly enforced?
- Rate limiting — is it applied only to login or should other sensitive endpoints be protected too?

---

### Category 2: Security & HIPAA Compliance

**What to audit:**
- **SSN Encryption**: Is `encrypt()` used on every SSN write path? Is `maskSSN()` used on every SSN read path? Are there any paths where plaintext SSN leaks?
- **PHI Data Exposure**: Are other PHI fields (medical history, medications, vital signs, progress notes) properly protected in API responses?
- **Security Headers**: Are the headers in `next.config.mjs` complete? Is CSP (Content-Security-Policy) missing?
- **Input Sanitization**: Is user input sanitized before database writes? Are there SQL injection risks via raw queries?
- **Error Messages**: Do error responses leak internal details (stack traces, query structures, table names)?
- **CORS/CSRF**: Are there any unprotected API routes accessible without authentication?
- **Password Handling**: Is bcrypt salt rounds (10) sufficient? Are passwords ever logged or returned in responses?
- **Audit Trail**: Is `AuditLog` model actually being populated? If not, which CRUD operations should create audit entries?
- **Environment Variable Safety**: Is `ENCRYPTION_KEY` properly validated on startup? What happens if it's missing?

---

### Category 3: Data Integrity & Validation

**What to audit:**
- **Zod Schema Coverage**: Do all API POST/PATCH routes use Zod validation? Are there routes that skip validation?
- **Schema-DB Enum Alignment**: Do Zod enums match Prisma enums exactly? (e.g., `ClientSchema` status enum has `DECEASED` but `ClientStatus` Prisma enum has `ON_HOLD` — is this intentional?)
- **StaffStatus Mismatch**: Zod StaffSchema uses `LEAVE_OF_ABSENCE` but Prisma enum uses `ON_LEAVE` — check consistency
- **Foreign Key Validation**: When creating visits, are `clientId`, `staffId`, `serviceId`, `carePlanId` validated to exist before the query?
- **Date Validation**: Is `endTime > startTime` validated globally? Are future dates validated where needed?
- **Cascading Deletes**: The Client DELETE route manually deletes related records before the client — is this because Prisma cascades are insufficient? Are any orphan records possible?
- **Transaction Usage**: Are multi-table mutations wrapped in `$transaction`? Are there race conditions in non-transactional operations?
- **Unique Constraints**: Invoice number generation uses count-based sequencing inside a transaction — is this truly safe against concurrent requests?
- **Pagination**: Is `limit` parameter bounded to prevent excessively large queries (e.g., `limit=999999`)?

---

### Category 4: API Design & Consistency

**What to audit:**
- **Response Format Consistency**: Some routes use `ApiResponse.success()`, others use raw `NextResponse.json()` — is the pattern consistent?
- **Error Handling**: Are all routes wrapped in try/catch? Do they all return consistent error shapes `{ error: string }`?
- **HTTP Status Codes**: Are correct codes used? (201 for creation, 204 for deletion, 409 for conflicts, etc.)
- **Sort Field Whitelisting**: Billing and staff routes whitelist sort fields — do all paginated routes do this?
- **Query Parameter Parsing**: Is `parseInt()` used safely with fallback for `page` and `limit`? What about NaN inputs?
- **Method Coverage**: Are there routes that export GET but not POST when they should support creation, or vice versa?
- **Route Organization**: Are there any dead or orphaned routes (defined in filesystem but unreachable or unused)?

---

### Category 5: Performance & Scalability

**What to audit:**
- **N+1 Queries**: Do list endpoints use `include` or `select` efficiently, or are there post-fetch loops that make additional queries?
- **Unbounded Queries**: Are there any `findMany()` calls without `take` limits that could return entire tables?
- **Missing DB Indexes**: Based on query patterns (WHERE clauses, ORDER BY), are all necessary indexes defined in the schema?
- **Large Payload Responses**: Do any endpoints return unnecessarily large payloads? (e.g., including all visits when only counts are needed)
- **Rate Limiter Scalability**: The in-memory Map-based rate limiter doesn't work across serverless instances — is this acceptable for production?
- **Visit Recurrence**: The recurring visit creation processes visits sequentially via `$transaction` — could this time out for large recurrence counts?
- **Seed File Size**: The seed file is 54 KB / 1,453 lines — is it structured efficiently, or does it have redundant data?
- **CSS Bundle Size**: `globals.css` is ~183 KB — is it optimized or does it contain unused styles?

---

### Category 6: Frontend Code Quality

**What to audit:**
- **React Best Practices**: Are effects properly cleaned up? Are dependency arrays correct? Is state managed efficiently?
- **Error Handling**: Do fetch calls handle errors gracefully with user-facing messages?
- **Loading States**: Does every data-fetching page show loading indicators?
- **Empty States**: Are empty data scenarios handled with appropriate UI?
- **Component Size**: Are any components excessively large (>500 lines) and need decomposition?
- **Prop Drilling**: Are there deep prop chains that would benefit from Context or state management?
- **Memory Leaks**: Are event listeners and intervals properly cleaned up?
- **Accessibility**: Do forms have proper labels? Are ARIA attributes used? Is keyboard navigation possible?
- **Inline Styles vs CSS**: Components use a mix of inline styles and CSS classes — is this consistent?

### Category 7: Business Logic Correctness

**What to audit:**
- **Visit Status State Machine**: Is there an enforced state transition graph for VisitStatus (12 states)? Can visits go from COMPLETED back to SCHEDULED?
- **Scheduling Conflict Detection**: Does conflict detection work for both staff and client overlaps? Does it handle timezone edge cases?
- **Invoice Amount Calculation**: Is the total computed from invoice items on the server, or can a client send a manipulated `amount`?
- **Payroll Overtime**: Is overtime calculated correctly based on hours worked per week?
- **Timesheet-Visit Linking**: When a visit completes, is a timesheet entry automatically created?
- **Medication Reconciliation**: Does `compareMedicationLists()` correctly handle name normalization and fuzzy matching?
- **Drug Interaction Checking**: Is the drug interaction database comprehensive? Are alerts surfaced to the UI?
- **Care Plan to Visit Generation**: Does the care plan visit generator correctly handle recurrence patterns (daily, weekly, bi-weekly, monthly)?
- **Insurance Claim Lifecycle**: Are claim status transitions (PENDING → SUBMITTED → IN_REVIEW → APPROVED/DENIED) enforced?

### Category 8: Naming Conventions & Code Consistency

**What to audit:**

- **Dead Code**: Are there unused variables, imports, or commented-out code blocks?
- **TODO/FIXME Comments**: Are there any unresolved TODO items in the codebase?

### Category 9: Architectural Concerns

**What to audit:**
- **Layer Separation**: Is business logic properly separated from API route handlers, or are routes doing too much?
- **Duplicate Logic**: The graphify knowledge graph shows `POST()` connected across multiple unrelated domains (medication reconciliation + report generation + employee ID generation from visit tasks route) — is this coupling appropriate?
- **Missing Middleware**: Is there no Next.js middleware for auth protection? Each route checks session independently.
- **Error Boundary Coverage**: There's one `ErrorBoundary` wrapping the dashboard — are error boundaries needed elsewhere?
- **State Management**: There's no global state library (Redux, Zustand, Jotai) — is `useState` + `fetch` sufficient for this app's complexity?
- **Code Reuse**: Are there duplicate implementations of common patterns (pagination, search, filtering) that could be abstracted?
- **Service Layer**: There's no service/repository layer between API routes and Prisma — all routes interact with Prisma directly. Is this sustainable?
- **Multi-tenancy Enforcement**: `organizationId` filtering is done manually in every query — could this be centralized via Prisma middleware or a helper?
